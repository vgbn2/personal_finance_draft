# Gemini CLI Mandates

This file contains foundational mandates for the Gemini CLI agent. These rules take absolute precedence over general workflows.

## 1. Professional Engineering Standards
- **Anti-Bullshit Testing**: Never hardcode values or forge massive JSON objects just to pass a test. Tests must verify real-world data patterns and edge cases using dynamic fixtures or historical slices.
- **The "Legacy GPT" Purge**: Much of the existing codebase was generated by legacy models (ChatGPT) and contains brittle logic (if/else proliferation) and hardcoded magic numbers. Actively identify and refactor these into **Schema-Driven Architecture**.
- **Dynamic Context**: Prioritize dynamic discovery (e.g., scanning the cache for symbols) over hardcoded defaults (e.g., `SPY/QQQ`).

## 2. Operational Directives
- **First Read**: For non-trivial work in this repository, read `skills/gemini/SKILL.md` before broad exploration so Gemini inherits the canonical repo workflow, truth map, and update rules.
- **Blast-Through Protocol**: When "blasting through", focus on high-signal architectural audits, identifying data gaps, and removing hardcoding.
- **Blast-Through Grading**: Every blast-through pass must assign a cleanliness grade to each major folder or section reviewed.
  - `A`: Clean, canonical, low drift, strong verification, minimal stale artifacts.
  - `B`: Mostly clean, a few contained debts or legacy gaps, no major confusion.
  - `C`: Mixed cleanliness, visible duplication, stale docs, or uneven verification.
  - `D`: Messy, overlapping active and legacy paths, debug leftovers, or trust gaps.
  - `F`: Fundamentally untrusted; cannot be treated as a reliable base.
- **Blast-Through Lenses**: Grade each section across path clarity, duplication/drift, verification quality, artifact hygiene, and doc alignment before assigning a final grade.
- **Blast-Through Output Shape**: Report strongest gap candidates first, then the section grades with a short reason for each, then the next cleanup move on the critical path.
- **Waterproof Architecture**: Every change must maintain the "Waterproof" standard-no silent failures, strict data validation, and clear process-bridge transparency.
- **Topic Integrity**: Always call `update_topic` at the start and end of major phases (Research, Strategy, Implementation, Testing) to maintain the narrative flow.

## 4. Safety & Anti-Corruption Mandates
- **Large File Protection**: **NEVER use `write_file` on files exceeding 500 lines.** If a file is large, you MUST use the `replace` tool or delegate to a `generalist` sub-agent. This is a hard safety limit to prevent accidental code truncation due to context window limits.
- **Surgical Verification**: Before applying any `replace` or `write_file`, run a targeted `read_file` or `grep_search` to ensure the target context is perfectly understood.
- **Immediate Recovery**: If any file corruption is detected, your immediate next move MUST be a `git checkout` or restore from backup before proceeding with any other tasks.
