## Update - 2026-06-23 session 56 — "/" chat suggestions + cursor-robustness fix + legacy-TUI engine switch (UNCOMMITTED)

User picked the conversation back up on session 55's typing-lag/cursor fix, asking whether anything
shaped like a command-suggestion dropdown would break the hardcoded `H-3` cursor math, then asked for
that feature plus a way back to the old TUI. Three rounds of iteration, each driven by direct user
correction:

1. **"/" suggestion dropdown + cursor robustness** (`sovereign_dashboard.mjs`, `chat_parser.js`
   `suggestCommands`/`allCommands` exported): typing `/` live-filters all manifest commands inside the
   same bordered chat box; ↑↓ cycles highlight, Tab fills the highlighted command into the input
   (TextInput already ignores up/down/Tab internally, confirmed from `ink-text-input` source — no
   double-handling), Enter strips a leading `/` and runs through the normal parser. Generalized the
   cursor-position math from a fixed `H-3` to `H-3-suggestionRowCount`, one shared variable feeding both
   the render and the cursor effect so they can't drift. Also fixed a **separate latent bug** that
   predated this session: the chat input row had no height cap, so a long typed command could wrap to
   2+ lines (Ink's default text-wrap) and silently break the cursor regardless of the new feature —
   capped that row to `height:1`+`overflowY:'hidden'` so it clips instead of growing.
2. **First "legacy mode" attempt (WRONG, corrected by user) — REVERTED:** built a `legacy_tui`
   feature-flag-then-`layout=legacy` toggle that just hid the chat bar inside the *same* Ink dashboard.
   User: "NO DIFFERENCE, shouldn't it just log out of this and point to the manifest" — there's a
   genuinely separate, older engine (`tui/engine.js`'s `runInteractiveMenu`, prompt-based, already
   toggled today via `LEGACY_TUI=1` env var in `sovereign_cli.js`'s `main()`) that the user meant, not a
   cosmetic dashboard variant. Reverted all of the dashboard-internal hiding logic.
3. **Real fix:** `Settings > Layout > legacy` (kept the layout-preset location, just rewired what it
   does) now makes the dashboard call `exit()` immediately after `settings layout --preset legacy`
   persists, and `sovereign_cli.js`'s boot loop re-reads the setting and launches the real
   `runInteractiveMenu` next. User then asked the natural follow-up: shouldn't switching back work too?
   Added the inverse in `tui/manifest.js` (added `'legacy'` to the legacy menu's own `--preset` options)
   + `engine.js`'s `runInteractiveMenu` (returns instead of looping back to its own menu when the user
   picks any preset other than `'legacy'`) + restructured `sovereign_cli.js main()` into a real loop.
   **Caught a self-inflicted regression before shipping it:** a naive "relaunch on every exit" loop
   would trap a normal `q`-quit in an infinite relaunch (neither engine's exit path distinguishes
   "user quit" from "switched layout" — both just end the child process the same way). Fixed by only
   looping when `loadSettings().layout` actually changed between the start and end of that run;
   otherwise the loop returns, ending the whole CLI exactly as before this change.
