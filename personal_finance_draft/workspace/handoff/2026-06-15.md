## Update - 2026-06-15 session 36 — backfill-daemon OOM fixed at the root + hard-tested + COMMITTED

User hit `backfill-daemon --once --concurrency 5` → `FATAL ERROR: JavaScript heap out of memory` (crypto
lane, ~4GB), twice. Root-caused, fixed at the root, hard-tested, refined the tests after user skepticism,
and committed (the session-35 batch above is now committed too).

**Root cause:** each crypto incremental job deserialized the entire multi-million-row 1m bin (BTCUSDT 1m
= 3.08M record objects, each w/ a fresh ISO string) **twice** — sink 1 = the merge-write in
`writeTsIndex` (read existing bin to merge-protect), sink 2 = `rollupFromBase` (read whole bin to derive
coarser TFs). At concurrency 3-5 across BTC/ETH/SOL → >4GB.

**Fix:**
- `validation.js` `mergeWriteBin`: `writeTsIndex` merges on the existing bin's **Buffer** (external mem,
  off-heap) via a two-sorted-stream merge — retained rows copied as 48-byte slices, only incoming rows
  become objects. Byte-identical to the old merge; also kills a latent `push(...existing)` RangeError.
  New `readTsIndexSince` (binary-search tail read).
- `data.js` `rollupFromBase(...,{sinceMs})`: incremental jobs re-derive only the recent UTC-day-aligned
  window (lossless).
- `backfill_daemon.js`: `LANE_MAX_CONCURRENCY={binance:3,alpaca:3}` clamps `--concurrency` on the 1m
  lanes; `docker-compose.yml` daemon `NODE_OPTIONS=--max-old-space-size=6144` (insurance).

**Hard test (user demanded "run it yourself"):** new `ts_merge_write.test.js` — byte-equiv (bin+meta) vs a
FROZEN reference transcription of the original merge + 3 real deep bins + a **child-process OOM
differential** (original child status 134 on a 1.3M-row bin under a 192MB cap, new child exit 0). After
user skepticism ("plan and fix those tests"), removed a durability bug (the test had used `git show HEAD`
as the golden ref, which breaks on commit) → frozen vendored reference + skip-safe git cross-check that
