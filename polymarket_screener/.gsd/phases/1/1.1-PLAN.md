# Plan 1.1: Scalable Project Structure & Configuration

## Objective
Set up a future-proofed directory structure and centralized configuration system that avoids hardcoded symbols and prepares for Render.com deployment.

## Context
- .gsd/SPEC.md
- .gsd/ROADMAP.md

## Tasks

<task type="auto">
  <name>Modular Project Structure</name>
  <files>None specific</files>
  <action>
    Create the following directory structure:
    - `config/`: Configuration and symbol registry.
    - `data/streams/`: WebSocket managers.
    - `data/clients/`: REST clients.
    - `data/storage/`: Local and MongoDB clients.
    - `strategy/`: Strategy logic.
    - `execution/`: Order execution and portfolio management.
    - `validation/`: Backtesting and stress testing.
    - `api/`: Frontend-backend connection (FastAPI/Flask).
  </action>
  <verify>Check directory existence via `ls`/`dir`.</verify>
  <done>Modular directory structure is initialized.</done>
</task>

<task type="auto">
  <name>Centralized Configuration (No Hardcoding)</name>
  <files>
    config/symbols.yaml
    config/strategy_params.yaml
    .env.example
  </files>
  <action>
    - Create `config/symbols.yaml` to store all asset identifiers (Crypto, Stocks, Polymarket).
    - Create `config/strategy_params.yaml` for thresholds and risk limits.
    - Create `.env.example` with placeholders for MongoDB URI and API keys.
  </action>
  <verify>Ensure YAML files are valid and .env.example contains necessary fields.</verify>
  <done>Configuration system is established with no hardcoded symbols in code.</done>
</task>

## Success Criteria
- [ ] Directory structure supports clear separation of concerns.
- [ ] All symbols are managed via `symbols.yaml`.
- [ ] Environment variables are clearly defined for cloud deployment.
